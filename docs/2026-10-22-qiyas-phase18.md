# Phase 18: measurement methods, dimension sheets and generated BOQs

The engine applies user-supplied rules to Phase 16 objects and Phase 17 recognition.
No measurement standard, trade thresholds, descriptions or rates are supplied with the product.
The invented methods in integration tests are test fixtures only. Development rules and runs
remain in `.local/`.

## Applied method and undo

`measurement.set_method` accepts `scope: settings | project` and a `method` snapshot (or null
to clear that scope). A project snapshot takes precedence over the Settings snapshot. Both
snapshots live in `QIYAS_KNOWLEDGE/measurement/selection`, inside the drawing, so quantities
can be reproduced after a method file changes elsewhere. The drawing-level project override
is available through the command surface; project-wide `.qss` propagation remains Phase 21 work.

The Settings loader validates `qiyas_dir()/methods/*.json` with the core schema. Changing
the selected method applies it to the active and parked drawings, one undo step per drawing.
Nested transactions roll every drawing back if any rule or saving Settings fails. New tabs
receive the selected method. The project snapshot keeps precedence. No settings file or
credential was read by the development agent.

`measurement.set_mappings` replaces drawing-owned BOQ mappings. `measurement.report` reads
applied methods, quantities, generated items, dimension sheets and review notes. Mizan uses
these commands through the existing registry; no extra AI tool is introduced. Generic
`set_knowledge` cannot bypass validation of measurement data.

The ordered derivation hook runs after objects and schedules and before fields. It writes
`measurement/result` only when its contents change. The existing document snapshot includes
this result, so geometry/property edits, method changes, deletion, undo, redo and DWG/DXF
round trips keep the same quantities and evidence together. The imported BOQ remains separate.

## Rule schema

The version 1 envelope remains `version`, `name`, `title`, `based_on`, `source_note`, `rules`.
Previously opaque rule payloads now require the following schema. Empty rule sets remain valid.

- Rules identify an exact element type, trade/category or both; an ID; a unit; dimension terms;
  optional unit bands, deductions, rounding and coverage notes. Every rule has `citation`:
  `{source, clause}`. No source or clause may be empty.
- Each dimension term has a label, `operation: add | deduct`, a timesing expression (default
  one), factor expressions and its citation. Values use physical units supplied by the object
  engine; coordinates used to place/edit geometry remain drawing units.
- A deduction selects a hosted opening/void type, its interior threshold predicate, a separate
  boundary predicate and boundary deduction predicate, and a cited deduct term. Boundary status
  can use measured coordinates/dimensions or explicitly supplied object properties. The engine
  does not invent a trade's boundary convention or discover undeclared voids.
- Unit bands have a predicate, unit and complete dimension/deduction recipe. Width and depth
  are ordinary expression properties. Overlapping applicable bands are errors. The base rule
  applies outside its bands.
- Rounding is per measured object, with decimal places, `nearest | up | down`, and a citation.
  It adds an auditable adjustment line before BOQ aggregation. Coverage notes each have a citation.
- Expressions resolve object properties, quantities and `geometry.*`, plus `void.*` for a
  hosted deduction. Drawing lookup tables are available through the existing expression engine.
  Unknown names, nonfinite values, negative operands and excessive deductions fail atomically.

Unresolved recognition/invalid geometry withholds the affected quantity. Every generated
quantity names its method and rule clause. Review notes identify objects without rules or
mappings. Methods are interpreted as data supplied by the user/Mizan; Qiyas does not verify a
rule's legal interpretation against a standard it has never received.

## Dimension sheets, BOQ and export

Lines retain timesing, factors, original expressions, resolved arithmetic, signed result,
inclusion decision, unit, method, citations and drawing references. Excluded deductions stay
visible. Each drawing reference has its driver handle, sheet, optional assigned `grid`
property and retained recognition/PDF evidence. Missing grids are explicitly reported for
review; no axis label is invented. Dimension arithmetic and totals use `qiyas-param`, using
its existing finite floating-point semantics.

Mappings supply code, English/Arabic description templates, unit, section, trade and citation.
Placeholders resolve object properties/quantities, type, level, trade and the rule's unit.
A mapping cannot silently convert units. A code cannot group incompatible units or descriptions;
include the varying property/unit in its template. No quantity is accepted in a mapping.

The BOQ panel shows generated items and expandable dimension lines, inclusion decisions and
source buttons. Settings notifications and the normal edit/undo refresh update the panel.
The existing export action includes `Generated BOQ`, `Dimension sheets` and `Measurement review`
worksheets in addition to the manual take-off. Both descriptions, clause/source references,
resolved arithmetic and excluded deductions survive Excel export. No rate column is generated.

The existing comparison engine consumes an adapter of the generated BOQ. Generated mappings
own their BOQ codes, preventing manual links to the same code from being counted twice.
The imported BOQ grid uses the same ownership rule, and comparison/source actions highlight
the generated item's drawing handles. Comparing preserves the client's imported BOQ and
remains one undo step.

## Benchmark precision and autonomy

`bench run --mode prepared` uses case-local recipes with shared-rule/geometric fallback.
`bench run --mode autonomy` never opens case-local recipes. It uses
`<root>/general/recognition.json` for CAD when supplied, otherwise the geometric baseline.
Shared recipes refuse explicit handles, placements, case IDs, file paths and constant extraction.
They may only define types and define/apply recognition selectors. This structural check cannot
prove that a human-authored selector is free of overfitting; shared rule provenance remains reviewable.

Both modes use the general vector PDF path, and prepared mode supplements its PDF recipes with
nonduplicate labelled-area measurements. `<root>/general/pdf.json` supplies calibration/label/
legend regexes. The calibration regex captures `distance`, with explicit physical unit conversion
and a search radius in text heights. A scale bar must have crossing ticks at both ends. Missing
or multiple calibration candidates are refused; raster pages are reported as unmeasured.
Adjacent PDF glyph fragments on a common baseline are joined using font-relative spacing
before reading calibration, labels and legends; their individual source handles are retained.
The product exposes the same import as `recognition.pdf_text`. Enclosures come from drawing
geometry, and legend entries can resolve symbol labels to descriptions. No page-specific
points, case filenames, gold quantities or truth IDs enter the general PDF predictor.

Coverage is item recall. Item precision is `matched / (matched + extras)`; item F1 is
`2 * matched / (truth + matched + extras)`. Empty submissions have undefined precision and zero
F1 when truth is present. These are identity measures; quantity accuracy remains separate.
Reports display all three per case and overall, with extra counts, and aggregate PDF results.
Mode-labelled reports are saved as `baseline-prepared.{json,md}` and
`baseline-autonomy.{json,md}` as well as immutable run directories. Original CAD handles cannot
be recreated from a PDF citation, so the scorer continues to report that traceability limitation.

## Machine-relative performance guards

`tests/support/performance.rs` times six sorts of the same deterministic two-million-integer
array in the test process. It is independent of rstar, geometry and the solver. The million
segment index must take less than 1.5 times that reference. A second assertion refuses a
reference so slow that a fourfold increase of the measured index time could pass the budget.
This preserves an explicit check for the codegen-unit regression, without a laptop clock floor.

Other algorithm timing guards use the same reference, with ratios proportional to their former
budgets (50 ms → 0.125, 250 ms → 0.625, 0.5 s → 1.25, 1 s → 2.5, 2 s → 5, 10 s → 25).
Functional wait/cancellation deadlines remain real-time checks: those verify time-based behavior,
not algorithm throughput. Test workload and correctness assertions remain intact.

## Benchmark comparison

Both modes completed once, serially, on 2026-10-22. All 1,099 cases produced identical
submissions across their three repetitions in each mode. There were 48,014 reference items,
including 980 PDF reference items across 120 PDF cases.

| Mode and scope | Matched / reference items | Coverage | Item precision | Item F1 | Extra items |
|---|---:|---:|---:|---:|---:|
| Prepared rules, all cases | 34,562 / 48,014 | 71.98% | 32.97% | 45.23% | 70,253 |
| General rules only, all cases | 31,922 / 48,014 | 66.48% | 32.22% | 43.41% | 67,153 |
| Prepared rules, PDF | 310 / 980 | 31.63% | 100.00% | 48.06% | 0 |
| General rules only, PDF | 190 / 980 | 19.39% | 100.00% | 32.48% | 0 |

Prepared rules add 2,640 matched items (5.50 percentage points of overall coverage) and
3,100 extra items relative to autonomy. The general PDF path measures 190 reference items
without case-local recipes. Combined with prepared recipes it raises PDF coverage from the
previous 120/980 (12.24%) to 310/980 (31.63%), an increase of 19.39 percentage points.

All matched quantities are within ±2%, but only 71.98% (prepared) and 66.48% (autonomy) of
**all** reference items are within that tolerance. Only 690/1,099 prepared cases and
150/1,099 autonomy cases reach 95% on that denominator. The portfolio acceptance target is
therefore not met. Low overall precision also exposes the many unmatched geometric candidates;
good accuracy on matched items must not be treated as a complete BOQ.

Scored traceability across all reference items is 70.82% prepared and 66.09% autonomy.
PDF traceability remains zero in this scorer because its reference handles belong to the
original CAD drawing, while PDF measurements cite the imported PDF entities. The new PDF
path retains its text, calibration and geometry handles, but this run does not prove their
correspondence to the original CAD handles.
