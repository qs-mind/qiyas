# W2: make Qiyas fast (27 October 2026)

The founder's words: "the program is very, very, very heavy". He wants it to feel like a native desktop
app. This is the measurement, the ledger of every attempt, what changed, and what is still slow.

Method: `performance-optimization` (measure, find the biggest cost, fix one thing, measure again, keep or
revert). Nothing here changes a number Qiyas reports: no quantity code was touched; the take-off of
`samples/test-plan.dwg` against `samples/test-plan.md` and the release guards are part of the final
`scripts/check.sh` run (result in "Final check" below).

Laptop limits kept: one heavy job at a time, `nice -n 15`, one cargo job, the heat guard watched (no
timing was taken during a pause: `scripts/perf` and `run.py` print the guard's lines; the engine runs show
`guard-paused-lines 0`, and every browser run started below 75 C). No sudo, no `perf_event_paranoid`
change: `perf`, `heaptrack` and `valgrind` are not installed here, so the profiles are timers, `/proc`
and Chromium's CPU profiler (see "Not measured").

Idle, the same binary after 25 s with nothing open: `qiyas-desktop` 1.2% of a core over three threads
(its main thread, the web view's receive queue, a vblank monitor), the one-second autosave watch is below

Other baseline findings, from Chromium with animations on (the real app has them on; W4's harness had
reduced motion):

* the heading of Mizan's panel always showed the animated Qiyas mark: about sixty SVG lines restyled sixty
  times a second for as long as the panel is open, plus the working dot's ring (a `box-shadow` animation,
  repainted every frame). 9.1% of a core with nothing happening, 601 style recalculations in 10 s.
* a pointer move over the drawing was a React state change in the app's root hook, so every move rendered
  the whole window: the ribbon (30 tooltips, 8 menus), Mizan's thread (one Markdown parse per message,
  8 per move with 8 messages), the tables. 5.7 ms of script per move in the production build.
* the layers panel put every layer in the page (about 25 elements each: 1,500 layers made 36,500
  elements) and rebuilt every row on each toggle.

## Ranked by what the user feels

1. The dev build itself: 2.4 to 3.7 times slower in the window, startup 1,075 against 690 ms in the real
   web view. Every interaction pays it.
2. A pointer move renders the whole window. Continuous: hovering, panning, every tool.
3. An edit, undo or layer toggle on a big drawing: the engine builds a batch of 0.1 to 0.8 s of which 85%
   is a click index, and the window receives all of it.
4. The layers panel on drawings with hundreds of layers (xrefs bring thousands).
5. Idle: an always-moving mark and a repainting dot (9% of a core).
6. Startup of the window itself: first paint, the web view's white before the CSS arrives.

Considered and not done, with the reason:

* Bundle splitting (one 1.46 MB chunk, 448 KB gzip). The Chromium CPU profile of the load shows 100 ms of
  script and a 50 ms first layout (inside Base UI's tab scrolling); the markdown stack is about 10% of the
  source. The expected saving is under 15 ms of 190: not worth the risk. Not tried.
* A background thread building the click index right after each batch: it would hide the first-snap cost
  and heat a core after every edit. Not tried (heat).
* An incremental batch (only the changed entities, an index that grows): the real fix for drawings of a
  million segments, and a rewrite of the batch cache. See "Still slow".
* `memo` on Mizan's panel and the tables: their props are rebuilt on every render of the app (the diff
  shows 40 changed props out of 40), so a `memo` does nothing until the hooks return stable objects. The
  remaining cost during a tool is 3 ms per move in the production build.
* Release profile settings (LTO, `panic = "abort"`, `opt-level` for the desktop crates): not measured,
  because a release build of the desktop app was not made on this laptop (heat, 12 GB of disk). The hot
  crates are already at opt-level 3 in the dev profile.
* A hidden window shown when the first frame is ready: needs the real window to check.
* The watch thread's one-second beat: measured at 0.026 ms, not a cost.

Nothing was reverted: every change that was measured beat its noise, and the ones that could not be
measured here are listed under "Not measured".

## The dev build

How much of "heavy" is the dev build itself, measured:

* the window: startup 1.55 times slower in the real web view (1,075 against 690 ms to a usable ribbon),
  3.0 times in Chromium; interactions 2.4 to 3.7 times slower (React's development build, `StrictMode`
  rendering everything twice, 250 modules, 16 MB over localhost, the unminified bundle);
* memory: 635 against 530 MB for the app and its web processes;
* the Rust side: the founder's dev profile already puts the engine (`qiyas-core`, `-geom`, `-render`,
  `-param`) and every dependency at opt-level 3, so batches, picks and snaps run at release speed;
  `qiyas-desktop`, `qiyas-ai` and the other glue crates are at opt-level 0, which this work did not find on
  any hot path (idle 1.2% of a core). It is the link of the 1.4 GB debug binary and the 20 minute first build
  that make the Rust loop slow, not what runs.

So most of what the window feels like in `pnpm tauri dev` is React's development mode. The honest fix is
to run the production bundle against the debug Rust app. The exact command:

```sh
pnpm tauri:fast
```

which is `pnpm tauri dev --config crates/qiyas-desktop/tauri.conf.json --config
crates/qiyas-desktop/tauri.fast.conf.json`: it builds the bundle (a second) and serves it with
`vite preview` on the same port. No hot reload: run the normal command when editing the window. The normal
command is unchanged. A fully optimised local app is `pnpm bundle` (release, with LTO off by default; about
30 minutes and 8 GB of disk on this laptop, not run). `pnpm tauri:fast` was not launched on a screen (no
window may open on the founder's; the equivalent was measured on the Broadway display).

## Still slow, and why

* A drawing of a million segments or more: every edit rebuilds the batch (0.18 s on 2.5 M segments after
  change 2, 0.03 s on 0.5 M) and sends all of it to the window (10 to 53 MB per edit), and the first click
  after an edit builds the index (0.11 s and 0.68 s). Fixing that is an incremental batch and index. The
  batch is derived data, so it is safe, but it is the largest change in this list and touches every edit
  path: left to its own piece of work.
* Peak memory of the engine on 2.5 M segments is 671 MB (the batch, the index, the encoded bytes and a copy
  the render cache keeps for a busy session, 53 MB each).
* A tool in progress (Distance, Line...) still renders the app on every move (3 ms of script in the
  production build, 10 ms in dev). The rubber band and the snap marker are computed in the app; moving them
  into the viewport's own store is the next step, then `memo` on the right column.
* Opening a drawing: dominated by the batch (0.14 s per 0.5 M segments), then the transfer.
* Unattributed: the web process used 4.7% of a core idle under Broadway; Chromium shows 0.37% with the
  busy dot only. Probably Broadway's repaint, not the app.

## Not measured, exactly

* Frame times of panning and zooming on a GPU. Chromium here uses SwiftShader (software GL): its draw times
  are not a GPU's and are not quoted.
* The real window on a screen: launch to first frame, the white flash (change 4), input latency with a
  real mouse, `pnpm tauri:fast` itself. No window may be opened on the founder's screen.
* A release build of the desktop app (launch time, idle, memory).
* The founder's own drawings and a long live Mizan conversation (the stub's conversation is 40 repeats of a
  11 event thread: long, not real).
* Heap profiles (no `heaptrack`) and CPU profiles of the Rust side (no `perf`): timers and `/proc` only.
* Engine timings in the release profile: the dev profile's hot crates are at opt-level 3 already; the
  release guards of `scripts/check.sh` ran, the examples were not rebuilt in release.
* Windows and macOS.

## Final check (27 October)

`scripts/check.sh` with one cargo job, `CARGO_INCREMENTAL=0` and two test workers:
- `cargo fmt` and `clippy` (all targets, warnings as errors) are clean. The first runs caught two lints
  in the new `bench_open` and `bench_edit` examples; both are fixed.
- `cargo test --workspace`, the pdfium tests and every release speed guard passed, including
  `pick_index_lazy`, `villa_speed` and `clinic_speed`.
- Vitest: 1,008 of 1,010 passed. `ConflictsPanel` and `AttachPdfDialog` each timed out once (5 s)
  while the heat guard was pausing and resuming the run. Both files then passed alone (14 of 14). The
  earlier `LayersPanel` timeout was the same kind and passed 3 of 3 alone. CI on GitHub is the clean
  run on a machine that does not pause.

## Skills

- performance-optimization: measure first, one change at a time, keep or revert, a guard per win.
- react-component-performance: a render counter found the churn (Markdown 8 times per move, 30 tooltips, the
  grids); fast state isolated, handlers stabilised, Markdown memoised, the layer list virtualised.
- react-state-management: the pointer moved out of root state into a store read with `useSyncExternalStore`.
- fixing-motion-performance: the box-shadow ring replaced by transform and opacity; a test keeps looping
  animations on cheap properties.
- performance: the Chromium load profile and bundle composition, which ruled out splitting the bundle.
- native-feel: the background painted before the CSS (first frame).
- rust-skills and memory-safety-patterns: the lazy `OnceCell` index inside the existing `RefCell` borrow,
  no re-entry, no new allocation or `unsafe`.
- incremental-implementation, debugging-and-error-recovery, code-simplification: one slice per commit with
  its test; the stale `data-layer-state` found by a test and fixed.
- source-driven-development: headless-tree's source for `scrollToItem` and focus, the repo's DataGrid
  for the virtualiser.
- documentation-and-adrs, observability-and-instrumentation: this report; timing marks in the harness only.
- Not applied: rust-profiling, linux-perf, flamegraphs, heaptrack, cpu-cache-opt (the profilers are not
  installed and their kernel setting was not changed); property-based-testing and dimensional-analysis (no
  number or unit changed); supply-chain-risk-auditor (no new dependency).
