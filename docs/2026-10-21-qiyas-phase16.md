# Phase 16: drawing knowledge and data-defined elements

The knowledge store and generic element engine use the existing command bus and three Mizan
tools. No model call is needed to define, draw, measure or schedule an element. Trade names do
not select behavior in the generic engine. All values are quantities, never rates.

## Stored data

`knowledge.rs` stores `{"version":1,"data":…}` in JSON string chunks in XRecords beneath
`NOD/QIYAS_KNOWLEDGE/<kind>/<name>`. Kinds are `types`, `levels`, `tables`, `rules`, `sheets`,
`mappings`, `views` and `measurement`. Writes invalidate stale raw DWG payloads. Unsupported
versions, malformed records and incomplete payloads are errors, not empty knowledge. The
store rejects aliased handles and inconsistent dictionary/XRecord ownership before mutation. The
objects and the named-object dictionary pointer are included in undo snapshots. The common
`xdata.rs` helper preserves UTF-8 chunk boundaries and discards only the edited application's
original DWG EED.

`define_object_type {definition}`, `redefine_object_type {definition}` and
`delete_object_type {name}` manage types. Deletion refuses instances anywhere in the drawing.
`set_knowledge {kind,name,data}` writes other kinds; it cannot bypass type validation.
`records` exposes `object_types`, `objects` and `knowledge_<kind>`; the latter also accept the
unprefixed kind names except where an existing records collection already owns that name.

A type contains `name`, `category`, `properties`, `geometry`, `vertical`, `plan`, `quantities`,
`join` and `host_cut`. Properties are number (with a unit kind, default and optional min/max),
text, choice or boolean. Geometry is point, path, region, band or hosted. Geometry expressions
cannot depend on quantities derived from that geometry. Unknown expression names and quantity
cycles are refused.

Plan recipes support outlines, band faces, solid hatches, centrelines, local symbol DrawSpecs
as JSON and label templates. Symbol strings beginning `=` are expressions. `unit` is metres
per drawing unit; divide physical sizes by it in symbol coordinates. Band widths and label
height expressions are in metres. An omitted label height uses the drawing's annotation size.
Union bands group by type, sheet and level. Automatic groups also share base and height;
explicit `assembly` identities permit mixed vertical spans. Each run retains its width and
justification. Contributions are assigned in driver-handle order from successive unions, so
their sum equals the union. The shared band service integrates volume between vertical
breakpoints and clips cut heights to their hosts. Overlapping cuts
on the same run and cuts too close to a junction are refused. Union joins currently require band geometry.
The geometry kernel refuses overlapping parallel runs within one union group; placement is
rejected atomically instead of silently counting duplicated material.

`place_objects {objects:[{type,points|driver,props?,level?,host?}]}` creates or adopts drivers.
`QIYAS_OBJECT` carries identity, type, properties and level on the driver. `QIYAS_OBJECT_PART`
identifies generated graphics by owner and recipe role. `set_object_props {targets,props,level?}`
validates and changes instances. Drivers and their generated content stay in one undo step.
Moving/copying/erasing a generated generic part resolves to its driver. Hosted cut stations and
widths are expressions in metres; hosts must be bands. A host cannot be erased while it still
has hosted objects. Copying a host together with its children remaps their host references.
Hosted definitions currently require a host-cut station; unsupported unanchored hosted types
are refused. Deleting a union's owner transfers its shared graphics to a surviving member,
preserving measurements and fields through the normal regeneration mapping.

Point symbols retain their local rotation and reflection through edits, undo and DWG/DXF.
`geometry.rotation` is expressed in degrees. Scaling a point driver changes its insertion
position; symbol sizes and measured quantities remain governed by explicit physical properties.
Use `set_object_props` to resize those dimensions. Hosted symbols follow their host tangent.

`object_schedule {at,filter,columns,group_by}` creates an ordinary CAD table with persistent
source metadata. Filters support type, category, level and sheet. Columns can name properties,
quantities, geometry facts, id, type, category or level. Numeric columns are summed within a
group and carry live `QiyasObject` field codes. Grouping, rows and values follow edits; position
and column widths remain as placed. A schedule can also be placed on a paper layout.

Example type (all business knowledge is in the command's data):

```json
{
  "type": "define_object_type",
  "definition": {
    "name": "Cable containment", "category": "Electrical", "geometry": "path",
    "properties": {"width":{"kind":"number","unit":"length","default":0.3,"min":0.01}},
    "plan": {"centreline":true,"label_template":"{type}: {run_length}"},
    "quantities": {"run_length":"geometry.length","surface":"geometry.length * width"}
  }
}
```

Geometry facts use metres and square metres, properties use their declared physical unit kind,
and placement points use drawing units. Quantity expressions can refer to other named
quantities. The `geometry.` prefix keeps source facts distinct from quantities of the same name.
Levels are knowledge entries with numeric `elevation` in metres. Lookup tables are JSON maps
of keys to rows, for example `{"A":{"factor":1.25}}`, read with
`lookup("table name", "A", "factor")`.

## Re-derivation and expressions

`Session::record_document_change` invokes one ordered pass list: objects, views, schedules,
BOQ rows, fields. Views and BOQ slots are extension points for later roadmap engines. The
passes run inside the existing recorder; a failure rolls the command back. The new object
commands also restore allocator state after failure, without changing successful undo's
monotonic handle allocation.

The expression parser supports powers (`^`, `**`), comparisons, `and/or/not` (and symbolic
forms), typed strings and booleans, lazy `if`, variadic `min/max`, `round(x[,places])`, `ceil`,
`floor`, existing trigonometry in degrees, and resolver lookups. Powers associate right;
rounding uses half away from zero. Numeric Arabic/Persian digits normalize; digits inside
strings stay literal. Parsing has length, nesting and node limits. Nonfinite calculations
are refused. The original numeric constraint API is preserved.

## Compatibility status

On open and after edits, the converter attaches typed instances to existing wall centrelines,
rooms and door/window inserts. Compatibility type definitions live in
`crates/qiyas-core/data/legacy-object-types.json`; the converter does not replace the visible
geometry. Joined wall quantities retain union, unequal-height and opening sill/head behavior.
The old wall property rebuild carries instance metadata through its existing handle mapping.

Door/window symbols are defined in the stored recipes and share the generic symbol evaluator.
Redefining a symbol recipe regenerates its block and repoints the existing inserts, preserving
placement, rotation, swing, schedules and quantity references. Imported legacy symbols are
adopted without replacing their visible geometry on open.

Legacy wall commands now translate their argument/result shapes into ordinary typed drivers
and the shared band service. The old wall tags retain compatibility for old API calls and
fields; they do not choose the geometry algorithm. Wall and room plan redefinitions generate
ordinary object parts. Opening offsets and reflection are expressions in the type data.
`property_bindings` evaluates read-only properties from expressions, including host properties,
primitive `host.*` geometry facts and `host.band_width`, so symbol thickness follows host edits.
Host-derived area/volume and named quantities are not supplied to bindings; derived area/volume
references are rejected to avoid circular derivation through the hosted cuts.

`object_regions.rs` owns retained seeded regions, holes, curved island boundaries and validity.
Any region type can bind a `region: {seed, subtract_islands}` source when placed. Boundary
search excludes retained drivers and their parts. Moving/copying/mirroring transforms the
source with its driver. An invalid enclosure marks only that object's record invalid and its
quantity fields show `####`; unrelated records remain usable. Old room metadata is retained
only for existing label, measurement and discrepancy interfaces.

Old room/opening schedules select recipes from `data/legacy-object-schedules.json` and use
`object_schedules.rs`. Generic schedule data supports `headers`, expression `templates`,
per-column `decimals`, selected `ids`, `totals`, `default_layer` and `preserve_overrides`.
Templates accept `{expression}`, `{expression:2}` and `{expression:6t}` (trim trailing zeros).
Old tables are adopted on open without replacing their handles, placement or manual overrides.
A detached room cell remains available to discrepancy checks until its source value changes.

## Verification and reviewer fixes

New tests define blockwork, slab, column, duct and kerb types through the Mizan tools, place
and measure them, generate field schedules, edit/redefine them, and exercise undo and DWG/DXF
without a project sidecar. Additional tests cover lookup tables, levels, unit invariance,
union joins, hosted cuts, copied hosts, generated-part edits and quantity-source remapping.
Storage tests cover all eight kinds and a second save after editing an imported DWG.
Compatibility tests compare joined wall, opening and room quantities across four unit systems.

The ResPlan converter validates an entire plan before writing a case. Invalid plans are logged
and skipped, and later plans are considered until the requested number of valid cases is
reached. The stdout report and `<source stem>.conversion.json` include rejected IDs and reasons.

`App.test.tsx` uses condition waits instead of fixed settling loops. Its file-local 30-second
budget accounts for rendering and querying the whole shell under load; other files keep their
existing budget. The requested five-repeat, two-worker run passed alongside an independent
CPU job pinned to the same CPU. Full check results and benchmark comparison are recorded in
the implementation report. Development artifacts remain under the git-ignored `.local/`.
