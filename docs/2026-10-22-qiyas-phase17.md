# Phase 17: evidence-driven recognition

Recognition rules live in `QIYAS_KNOWLEDGE/recognition`. Mizan supplies interpretation;
Qiyas computes geometry, validates properties and derives the Phase 16 object quantities.
No trade name selects an algorithm. The villa is not a special case.

## Commands

Discover `recognition` through the command registry. The wire form is
`{"type":"recognition","kind":"…"}`. The same commands serve the window, Mizan,
MCP and scripts.

- `define {rule}` inserts or replaces a validated rule. A rule names an `object_type`,
  a `match` selector, property `extract` expressions, `confidence`, `review_below`
  (default 0.9), and an optional integer `priority`. Equal-priority competing rules
  require review. `reject: true` records a negative recognition rule.
- `list` reads definitions. `test {rules?: []}` is a dry run. `apply {rules?: []}`
  applies the same proposals in one undo step. Reapplying skips existing recognition
  decisions and typed drivers.
- `queue {state?: pending|accepted|rejected}` reads decisions on the current sheet.
  `review {handle, decision, props?, object_type?, save_as?, rule?}` accepts, fixes or
  rejects a pending proposal. An unresolved extraction still applicable to the corrected type must be explicitly corrected.
  Changing type discards incompatible old properties and rechecks the source geometry.
  A correction named with `save_as` becomes a rule scoped to its source handle. Supply
  `rule` to express an intentionally broader new or edited rule. Generalisation is
  never inferred from one correction.
- `read_schedule {source}` reads actual table cells, delimited MTEXT/text grids or
  named block attributes. `schedule {spec}` uses caller-supplied columns to define
  types and matching rules, retaining the source handles. This also covers legends.
  No door, window, finish, column name or unit conversion is assumed by the engine.
- `pdf {path, page, calibration, insert_at?}` imports vectors through pdfium. The
  calibration is `{a, b, distance_m}`: two displayed page points and their physical
  separation. Qiyas converts that into drawing units per PDF point. Imported entities
  retain their source path and one-based page in `QIYAS_SOURCE`.
- `vision {spec}` accepts bounded PDF page hints, calibrates them, and snaps them to
  existing CAD geometry or nearby raster ink. Page coordinates have a bottom-left
  origin and y up. A missing snap or raster interpretation remains pending. Accepting
  a candidate creates its typed instance; neither an image nor Mizan supplies a quantity.

Selectors support case-insensitive globs (`*`, `?`) or `{regex: "…"}` for layer,
block, entity type, attribute values, hatch pattern and text; effective RGB colour;
closed regions; and explicit source handles. Closed regions can be traced around text
insertions using the existing boundary engine. Property extraction supports attribute
numbers/text, regex captures from a note or section label, overlapping parallel-line
spacing, geometric length/area/count, and explicitly cited constants. Numeric text
accepts Arabic and Persian digits. Properties use physical units; coordinates use the
drawing's units. Search distances are supplied in metres. Missing or ambiguous evidence
is reported, not silently substituted into accepted quantities.

Recognition types use an empty plan recipe and no host cut, preserving the consultant's
source graphics. Existing driver shapes are reused where compatible; a text's point or
seeded region gets a linked driver. Confident matches become Phase 16 instances immediately;
pending matches retain their proposed placement without publishing an instance quantity.
Every apply, schedule import, calibrated PDF import, vision submission and review is one
undo step, including knowledge, source metadata and resulting geometry. Decisions and
rules round-trip in DWG and DXF.

## Window and documents

The Review tab shows confidence, rule, source page/handle and unresolved evidence. It
supports Accept, Fix properties/type and Reject, with a correction-rule option. Its
controls have English and Arabic translations. Reads are invalidated on drawing changes;
a late response cannot populate another drawing's queue. Mutations use the existing
redraw, information refresh and autosave path.

`qiyas_read document {path, pages?}` returns plain page text on the single pdfium worker,
without an open drawing. Pages are one-based; omission reads the first 20 and lists the
remaining pages. At most 100 pages and 2 MiB of text are returned per request. Empty text
explicitly needs vision; there is no fabricated OCR. `qiyas_capture` source `document`
accepts `{path, page, width?}` and returns pixels with a page-coordinate conversion caption.
Neither operation changes the drawing or history.

The composer accepts PDFs by file picker, drop or paste, as well as pictures. PDFs up to
20 MiB are validated through pdfium and stored under the Qiyas data home's `attachments/`,
with random file names. A message carries the attachment's name, path and page count so
Mizan can read or capture it. Debug builds use `.local/qiyas-home`; no settings file or
credential is involved. Attachments are retained for resumed conversations.

## Benchmark interface

`qiyas-cli bench recognize --case ID --plan FILE --output FILE` evaluates a recognition
recipe and writes a computed submission. `bench run` automatically uses a case-local
`recognition.json` when present, falling back to the existing geometric baseline otherwise.
A recipe contains `commands`, `measurements`, and optional `include_baseline`. Commands
are limited to type definitions, recognition and PDF import/underlay operations. File
reads stay inside the development case directory, with symlink and holdout checks.
Commands use the shared offline batch surface, including prior-step references for
reviewing a vision result. No model or provider settings are used.

Each measurement selects `object_type`, a named derived `quantity`, `kind`, and `unit`.
Optional fields are `id`, `description`, `basis`, `aggregate`, and `height_property`.
The recipe has no submitted quantity field. Only valid, accepted objects contribute.
Pending proposals are counted in warnings. The prediction runner never reads truth files.
The report retains the previous rates for comparison, and the previous complete baseline
was preserved under `.local/phase17/baseline-before.json` before this task's final run.

Scoring tolerances, missing items, extras and CAD citation checks remain unchanged.
PDF page citations are retained; they do not pretend to reproduce original CAD handles.
Controlled offline scan hints test the recognition/measurement interface, not a live
model's visual judgement. Paid/live Mizan evaluation was not requested or run. Development
recipes and their preparation/review records are under `.local/phase17/`; case-local
recipes are under `.local/benchmark/cases/`. Native recipes interpret visible drawing
notes. PDF recipes use visible calibration marks and reviewed symbol points. Recipe
preparation does not read truth quantities; only the unchanged scorer reads them.

## Boundaries

Recognition currently acts on the current drawing's own top-level entities. Xref contents
remain read-only; nested block contents are represented by their top-level block reference.
No automatically guessed trade rules ship with the engine. Unmatched linework needs a
broader rule or a vision hint before it can become a review candidate. Raster snapping
is limited to nearby ink and is not semantic OCR or a proof of vector accuracy.

The 95% consultant-portfolio recognition target requires independent senior-QS validation.
The development benchmark is evidence about its included cases, not proof of that target.
The imported clinic drawings also lack sufficient retained model identity and 3D evidence
for the existing scorer to reproduce all their IFC quantities from planar outlines.

## Dependencies

No new crate was added to the lockfile. `regex` is now a direct core dependency for bounded,
non-backtracking data patterns (MIT OR Apache-2.0). Existing workspace `qiyas-pdf` and
`uuid` dependencies are reused for document reads and attachment names. No GPL code,
paid assets, live model calls or cloud rendering were used.

### Benchmark comparison

The current development folder has **1,099 cases**, including **143 ResPlan cases**
absent from the saved 956-case Phase 16 report. The comparison below uses only those
original **956 cases**. Their reference item IDs, quantities and tolerance classes are
unchanged; the baseline and current common cohort both contain 44,477 reference items.

|---|---:|---:|
| Coverage | 65.0314% | **70.9670%** |
| Matched items | 28,924 | **31,564** |
| Matched accuracy within 1% | 100% | **100%** |
| Strict tolerance pass rate among matches | 99.9965% | 99.9968% |

Coverage increased **5.9357 percentage points** on the identical reference cohort.
There is still one strict-tolerance miss, and extras increased by 3,100; the matched
accuracy figure does not mean complete precision. Imported clinic coverage remains zero:
those planar source drawings do not provide the retained identities and 3D evidence
needed by their existing reference quantities.

Across the full current set, coverage is **71.5875%** (34,372 / 48,014), matched accuracy
within 1% is **100%**, and the strict matched pass rate is **99.9971%**. All **1,099** cases
have identical submissions across all three repetitions. No recognition recipe failed.
The run took **2,603.38 seconds** (43.39 minutes), compared with 1,542.31 seconds for the
saved baseline; the case sets and runtime conditions differ, so this is not a controlled
performance comparison.
