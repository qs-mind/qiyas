# Phase 21: project scale and Mizan live-run fixes

Projects extend the existing sheet-set format with an optional `project` record. They live in
`qiyas_dir()/projects/*.qss`. The data-home implementation now belongs to core, with the same
release/debug/environment override rules used by the window. A project in that directory can
reference absolute DWG/DXF paths. Other sheet sets retain relative paths inside their folder;
existing symlinks are checked against that boundary too.

The registry exposes `project.create`, `open`, `list`, `add_drawing`, `remove_drawing`,
`set_method`, `set_checks`, `set_register_rules` and `run`. Examples and schemas are generated
from the command definitions. Each edit records one project-file undo step, including a run's
aggregate and checks. Undo/redo refuse to replace a file changed externally. Drawing batches
refuse project commands. The desktop keeps project history separately so projects work with no
open drawing. Exported workbooks and reports are snapshots, like existing take-off exports.

A run opens isolated drawing sessions and reuses core script parsing/execution from the
existing batch machinery. It applies the project method override, reapplies drawing-owned
recognition on every sheet, and reads the generated measurement report. Missing interpretation
is reported; no standard, trade vocabulary or quantities are inferred by the batch runner.
Mizan interprets and saves each drawing before running the aggregate. The desktop refuses a run
with unsaved member drawings. Original drawing knowledge is never moved into the `.qss`.

Aggregation keys are mapping code, section, trade and unit. An empty code uses a normalized
description key. Different units stay separate. Every item retains contributions by drawing,
including its generated quantity and complete dimension lines, operands, source handles,
sheets, grids, methods and citations. The project override governs every member for the run;
opening a drawing independently retains its own method selection.

Phase 19's evaluator now accepts a context spanning separate drawings. Element sets may name
`drawings`; table sources name `drawing` alongside their sheet/handle or extracted table name.
No drawing or knowledge dictionaries are merged. Host/id joins and finding references distinguish
drawing paths, avoiding collisions between CAD handles in different files. Cited rules can
compare schedules against aggregate instances, test quantity relations, membership or duplicate
identity. Queries retain stable status and notes on reruns. Unreadable members and failed checks
are reported as incomplete checks, never as a clean result.

The drawing register uses explicit data: a target field (`number`, `title`, `revision`, `date`),
an attribute tag or a regex with a value capture, and optional layer/block/sheet selectors.
Missing values and multiple distinct matches are flagged. The engine does not supply tag names,
a drawing number or today's date. Register rows retain their evidence handles.

`qiyas-cli project run <project.qss> [--out folder]` writes `project.xlsx` and
`morning-report.md`; without `--out`, outputs go beside the `.qss` in `<project>.output/`.
The workbook contains Generated BOQ, Dimension sheets, Queries, Register, Drawings, review notes
and a chunked lossless Project record. Its project record round-trips through
`qiyas_boq::project::import`. A partially failed run still writes the successful quantities and
failure report, then exits 1. Incomplete checks exit 2.

The English/Arabic Projects panel lists the data home's projects, creates/opens a project,
adds/removes drawings, runs it and shows status, warnings, register gaps and output paths.
Controls use the existing CSS brand tokens and UI stack. Mizan's host uses the same project
workspace; members of the selected project can be opened without repeated file confirmation.
The workflow directs Mizan to interpret each drawing, supply project checks/register rules,
run the aggregate and report uncertainty without a required human review step.

Busy/rate-limit HTTP replies (429, 503, 529) use one policy in normal and budgeted providers:
5, 15, 45 and 55 seconds, bounded by a two-minute window. `Retry-After` seconds or HTTP dates
are a lower bound. A server delay longer than the remaining window fails without retrying early.
Rejected retries retain one budget reservation, charge no unknown usage, and do not consume the
successful-request allowance. Tests use virtual time, including success after the old three-call
limit and exhaustion of the full window. No live provider calls were made.

The take-off kit declares `complete: true` and includes a project path. Covered command discovery
returns the same short kit entry, with a flag identifying it as already supplied. Full validation
repairs remain available for malformed inputs. The existing 6,144-byte size guard is retained.

## Benchmark

`bench projects --set quick --mode prepared|autonomy` runs the project diagnostic alone; ordinary
quick benchmark runs include it too. Inputs use existing clinic architectural storeys, duplex
storeys and generated apartment floors. Quick uses the first three drawings in each family.
Each family has a clean control and a copy with planted schedule/identity discrepancies.
Those cross-drawing probes are synthetic and explicitly labelled; BOQ truth comes from the
original development cases. Neither prediction nor Mizan reads truth. Private input copies,
projects, workbook/report and prediction JSON are written before scoring reads quantities and
check truth. No new source downloads or licences were needed.

Coverage and item precision are scored on the combined project BOQ. Quantity accuracy is separate.
Checks are scored by rule identity, including clean false positives. Submitted items retain the
measurement basis declared in their input recipe; no gold basis is copied into a prediction.
`bench projects --rescore <report-folder>` scores saved predictions again without running
interpretation or changing their workbooks. This is an engine diagnostic,
not a live MIZAN ALONE result or evidence that real project take-off coverage meets the roadmap.

## Measured project results

The prepared full quick run stopped at the new project fixture after completing its 120
predictions and revision diagnostic. The required text-property default was added, the CLI
rebuilt, and only `bench projects --set quick --mode prepared` was rerun (exit 0, six projects).
The autonomy full quick run then completed once (exit 0, 120 drawings and six projects).
Its existing drawing-level coverage is **19.4989%**, item precision **98.7586%**, and discrepancy
recall **100%**.

Inspection of project scores found that submitted items had all been labelled `geometric`,
losing explicit rule bases from the input recipes. The scorer now derives that metadata from
those recipes and writes its submission before opening truth. The focused regression passes
with an unreadable truth path. Final CLI Clippy and build passed. Both saved project suites
were rescored with `bench projects --rescore`; no take-off was repeated. All 24 prediction JSON
and workbook SHA-256 hashes remained unchanged. Original results are retained alongside the
corrected `project-rescored.json` files.

Each mode contains six projects: clinic storeys, duplex storeys and apartment floors, each with
a clean control and seeded copy; three drawings per project. The project BOQ scores below count
both copies. There are 9,398 combined truth items overall (4,335 per clinic project, 355 per
duplex project and nine per apartment project).

| Mode / scope | BOQ coverage | Item precision | Matched / truth | Extra items |
| --- | ---: | ---: | ---: | ---: |
| Prepared, all projects | 0.0851% | 40% | 8 / 9,398 | 12 |
| Autonomy, all projects | 0.1064% | 100% | 10 / 9,398 | 0 |
| Prepared, apartment floors | 44.4444% | 40% | 8 / 18 | 12 |
| Autonomy, apartment floors | 55.5556% | 100% | 10 / 18 | 0 |
| Either mode, clinic and duplex | 0% | No submitted items | 0 / 9,380 | 0 |

Both modes found **6/6 expected cross-drawing rule findings**, predicted exactly six rule
findings, and raised none in the clean controls: **100% recall and 100% precision**. Scoring is
by rule identity within each project, not individual RFI count. All matched quantities passed
their tolerance checks. Traceability is present in the exported dimension sources and tested
independently; the single-drawing scorer does not remeasure a multi-drawing project's traces.

The IFC families have no case-specific prepared recipe and the available shared recognition
does not generate their BOQs. Those omissions remain in the denominator. The apartment prepared
recipes leave gaps and extras too. These results validate the project machinery and expose
recognition coverage limits; they do not establish complete autonomous real-project take-off.
No live provider evaluation was attempted and no decision is outstanding.
